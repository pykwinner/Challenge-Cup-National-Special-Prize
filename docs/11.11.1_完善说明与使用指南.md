现金费用清单为 operating、carbon、fixed_om、startup_shutdown、biomass_fuel；CVaR、缺热和舒适度等优化处罚不直接计入企业现金流。固定运维可选择：

- `finance.fixed_om_method: proxy_plus_model_adjustment`：默认，保留原累计投资比例运维代理；模型固定运维调整已包含在经营成本中，只计算一次。
- `finance.fixed_om_method: modeled_only`：明确停用该代理，仅使用模型现金费用。当前模型尚未完整建立所有既有资产固定运维基线，不应误认为此选项自动补齐了基线。

远期确有建设义务时，联合配置可以显式指定 `future_build_obligations`，包括 `decision_year/category/asset/option/value`。它用于明确工程义务，不允许模型自行靠尚未投产资产的残值获取收益。终端现金流行使用 `is_terminal: true`；旧财务表若无此字段，仍按每行一个经营年处理。

## 2. 验收与结果追溯

每次模型求解新增通用数值审计：完整约束、变量上下界、整数性和实际求解目标重算。它保存本次求解的目标向量，因此碳目标求解后恢复成本向量不会导致错误审计。报告包含最大绝对违反量、归一化违反量和异常位置。

默认绝对容差为1e-6、相对容差为1e-8；归一化违反量按相应侧边界及行活动量计算，≤1为通过。下界与上界分开归一化，较大的另一侧界不会掩盖负容量。整数偏差单独以绝对容差判断。

储热后检查现在独立重算**所有时段**的状态方程、SOC上下界、充放功率界和互斥；同时要求每个资产、边界组和预期时刻都有完整且不重复的证据。只有首末库存正确、中间状态错误的轨迹也会失败。

年度证书增加数值审计、储热证据完整性、全轨迹状态和启停诊断门槛。代表时段覆盖仅接受明确的`pass`，并补充冷负荷的峰值、能量和爬坡检查。旧结果若没有新增数值证据，不会自动获得新标准下的通过证书，需要重新求解或提供可核验的完整证据。

年度批处理的缓存身份包含继承后完整配置、数据内容、算法源码、软件版本及影响输出的选项。只有认证字段明确通过、必要产物完整、内容哈希一致，且运行前后输入身份一致，才原子发布完成标记。重跑时原输出保存在`.batch_history`中。历史文件仍在不代表新任务成功；无可信完成标记的旧缓存不直接复用。

风险扫描也必须在同一实验身份内比较，不能将新参数下的部分权重结果与旧实验汇总混合。没有零权重基准时，不应把第一个风险权重冒充风险中性。

这些审计证明当前数学模型及已独立重算的物理量满足要求，不代表所有水力、设备非线性和现场参数都已验证。

## 3. MPC现在支持的范围

窗口和执行步长以小时输入，必须是物理时间步的整数倍，且执行步长不得大于窗口。末尾不足完整窗口仍执行；每个时刻恰好覆盖一次。固定投资不再放松可靠性要求，并检查配置中是否仍存在可变投资。储热SOC逐窗承接，最终窗口保留指定期末库存要求。

当前支持单场景、单状态组、权重为1的连续热源—管网—储热调度。机组启停、建筑惯性、燃料库存、电池和需求移峰尚未完整跨窗承接，入口会明确拒绝这些组合，不再循环重置状态后继续报告结果。

MPC使用调用者提供的未来输入，还没有独立预测误差模块。完整在线控制、终端价值和其余动态状态传递仍是后续工作。

## 4. 独立供暖季验证

新增模块入口：`heatplan.heating_season_cli`。它先在给定规划时域求解并冻结投资，再按明确的服务窗口回放，输出独立的`heating_season_acceptance_certificate.json`。

输入范围是带时区的`[start_inclusive,end_exclusive)`。必须逐个时间戳精确匹配，不能只满足行数。无时区输入必须指定其真实`--input-timezone`；NASA当地太阳时LST应在上游按明确约定转换，不能直接标成北京时间。

若用户行为依赖场景名，保留源数据唯一场景或用`--operating-scenario`显式指定映射；未知场景不能静默将非1行为乘数改成1。

正容量储热要求显式`initial_soc_fraction`和`final_soc_min_fraction`，并在季节回放使用固定边界。其他动态模块缺少独立初值接口时默认拒绝；只有用户显式使用`--allow-cyclic-state-assumptions`才采用现有循环模型，并将全部假设写入证书。这种证书验证的是所声明假设下的模型，不是已知现场初态的连续运行。

年度碳限额、年度燃料采购量、地源冬夏平衡及年度经济预算/热价等不会被静默套在冬季分母上：它们保留在原规划阶段，季节回放列出`deferred_annual_constraints`，要求另做全年补充。季节能量、排放和运行费用以`_over_period`输出；不生成全年与季节总量的虚假差值，不把年度固定费用自动按季分摊。

### 可直接运行的软件演示

工程提供`examples/heating_season_smoke`三个输入文件。这是跨2024—2025年的**4小时人造软件案例**，总需求6kWh、运行费用6元，不是任何城市的真实供暖季。

在主工程目录中运行：

```powershell
$env:PYTHONPATH = "$PWD/src"
python -m heatplan.heating_season_cli --config examples/heating_season_smoke/config.yaml --representative-timeseries examples/heating_season_smoke/timeseries.csv --chronological-timeseries examples/heating_season_smoke/timeseries.csv --scope-file examples/heating_season_smoke/scope.json --output outputs/software_smoke_11_11_1 --planning-time-limit 5 --replay-time-limit 5
```

真实城市使用现有`data/heating_season_scopes_2024_2025.json`并以`--profile`选场景，替换为已补齐且时间口径明确的实际逐时输入。可先加`--preflight-only`检查窗口；预审通过不会产生已求解认证。

主要输出：季节范围审计、冻结配置、投资冻结表、规划投资、季节调度、储热轨迹审计、季节指标和季节证书。`run_identity.json`记录合并配置、实际数据内容指纹、源码和依赖身份、求解设置；季节证书绑定该身份和输出文件哈希。`annual_replay_certified`始终为false，不能用季节证书替代全年验收。新运行开始时先将成功状态置为未完成，输入读取失败也不会留下旧通过证书。
