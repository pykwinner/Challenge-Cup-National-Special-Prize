## 2. 为什么容量审计之后仍需完整年度回放

V11.8的跨年度可靠容量审计回答的是“装机和配电容量在峰值上是否足够”，但不能完整回答以下运行问题：

- 逐小时启停、最小出力和爬坡约束能否同时满足；
- 储热在连续寒潮中的能量而非功率是否足够；
- 代表日边界与全年首末状态是否引入不可实现的能量借用；
- 热泵、电锅炉、循环泵和微网电力负荷是否在同一时刻争用配电容量；
- 武汉可逆热泵在冬季供热和夏季供冷之间共享容量后，能否同时保持零失供；
- 固定投资在年度回放构模过程中是否发生候选容量“偷偷回开”。

因此，完整年度回放不是重复计算，而是把容量充分性进一步升级为运行可行性。

## 3. 固定投资检查点算法

### 3.1 数学关系

V11.8先求解两阶段随机规划：

\[
x^*=\arg\min_x\left\{C^{\mathrm{inv}}(x)
+\mathbb E_s[Q_s(x)]+\lambda\operatorname{CVaR}_{\alpha}(Q_s(x))\right\},
\]

其中，\(x\)为三场景各自的投资变量，\(Q_s(x)\)为气象年场景\(s\)的运行成本。V11.9不再改变\(x^*\)，而对筛选出的完整年度\(y\)分别求解：

\[
\min_{u_y}\ Q_y(x^*,u_y)
\quad\text{s.t.}\quad
g_y(x^*,u_y)\le 0,
\]

其中，\(u_y\)包含8760/8784小时的供热、供冷、储能、启停、需求响应和网络运行变量。不同年度只共享冻结后的投资，不共享运行状态或储能边界。

### 3.2 检查点内容

每个场景检查点保存以下必要对象：

- 代表情景规划的`summary.json`、`investments.csv`和`dispatch.csv`；
- 已冻结候选投资的`fixed_investment_config.yaml`；
- 逐资产`investment_freeze_audit.csv`；
- 变量数、整数变量数、约束数、建模时间和求解时间画像；
- `fixed_plan_checkpoint_manifest.json`完整性清单。

检查点不会伪造求解器内部状态，也不会尝试恢复已经无用的完整变量向量。年度回放只依赖规划KPI、投资表、冻结配置和冻结审计，因此以最小必要状态重建`SolveArtifacts`，降低跨进程复用负担。

### 3.3 五层防串用校验

加载检查点时依次执行：

1. 必需文件和目录边界校验，禁止清单路径越出检查点根目录；
2. 每个文件的SHA-256完整性校验；
3. 原始规划配置的规范化指纹校验；
4. 代表时序的数据指纹、行数和气象年场景集合校验；
5. 用当前投资表重新冻结当前配置，并逐资产复算`freeze_ok`。

CSV往返可能产生约\(10^{-13}\)量级的浮点尾差，因此结构字段要求完全一致，数值字段采用绝对容差\(10^{-8}\)、相对容差\(10^{-10}\)。这一容差仅用于检查点同一性判断，不放松模型物理约束或验收门槛。

已有V11.8结果只需先执行一次无求解迁移：

```powershell
$env:PYTHONPATH='src'
python scripts\index_fixed_plan_checkpoints.py `
  --manifest outputs\v11_8_multiyear_stochastic_bundle\stochastic_multiyear_manifest.yaml `
  --checkpoint-root outputs\v11_8_multiyear_stochastic_readiness
```

```powershell
$env:PYTHONPATH='src'
```

## 9. 结论边界与下一步

V11.9已经证明V11.8定稿投资在筛选出的最不利年度集合中具备逐小时运行可行性，但仍需保持以下边界：

- 回放覆盖7个多指标筛选极端年，不等于穷举全部15个“场景—年度”组合；
- 气象来自公开再分析数据，负荷仍由可审计工程参数映射生成，不等同于城市热力公司实测SCADA；
- 当前管网是规划级热力—水力后校核，不是瞬态水力仿真；
- 认证结论只对当前输入、配置和检查点指纹成立，参数变化后必须重新规划或重新认证。

下一步最有价值的算法工作是对CVaR权重\(0,0.02,0.05,0.10\)执行投资稳定性扫描，并用检查点机制只对发生实质投资变化的候选方案运行完整年度回放。这样可以回答“风险厌恶程度提高到什么位置后，方案结构才真正变化”，为答辩中的风险偏好选择提供量化依据。
